# Specifying User Interfaces

Load this when a capability spec covers user-facing behavior — screens, panels, forms, editors, wizards, dashboards. It shows how to express UI as **normative, observable behavior** inside the existing `SPEC.yaml` sections. No schema change: UI does not get its own top-level keys.

## The golden-rule-D guardrail (read first)

A UI spec captures intent the **code cannot carry**: which states exist, which transitions are legal, what an interaction guarantees, when an error or progress signal must appear, and *why*. It MUST NOT transcribe what the component code already shows.

- ❌ Transcription (delete it): "the SaveButton has props `disabled`, `loading`, `label`." That's the code.
- ✅ Contract (keep it): "While a save is in flight, the surface MUST reject a second save submission and MUST show progress until the save resolves or fails."

**Test:** if your requirement could be regenerated by paraphrasing the component's props/markup, it's duplication — cut it or replace it with the intricacy it was burying (a transition guard, a timing rule, an error contract).

## Where UI lives in SPEC.yaml

| Existing section | UI content it carries |
|------------------|-----------------------|
| `actors_and_surfaces` | The **pages/surfaces**: who triggers behavior through which screen/panel, and what each surface is responsible for. |
| `state_and_lifecycle` | The **state machine(s)**: states, transitions, initial/terminal states, illegal transitions, and async/timing semantics. |
| `requirements` (`REQ-`) | **Interaction contracts** and behavior MUSTs — the normative guarantees of events, inputs, navigation, shortcuts. |
| `failure_modes` (`ERR-`) | **Error/warning surfacing**: each user-facing failure's condition and its observable UI behavior. |

## State machines (in `state_and_lifecycle`)

Enumerate the states and the transitions between them. Use a compact, consistent notation:

```
States: Empty, Loading, Loaded, Saving, Error
Initial: Empty
Terminal: (none — surface is long-lived)

Transitions (event [guard] → target / effect):
  open            → Loading
  loaded          → Loaded
  edit            → Loaded            (stays; marks dirty)
  save [dirty]    → Saving            / persist begins, progress shown
  saved           → Loaded            / dirty cleared
  saveFailed      → Error             / ERR-XXX surfaced, edits preserved
  retry           → Saving
```

Specify the things code can't show on its own:

- **Initial state** and any **terminal states**.
- **Illegal transitions** that MUST be impossible (e.g., "no transition leaves `Saving` except `saved` or `saveFailed`").
- **Async/timing semantics**: what happens to user input during `Saving`; whether stale responses are ignored; debounce/coalescing of rapid events; ordering guarantees. This is the high-value content — name it explicitly.
- **Loading/working states are first-class**, not afterthoughts — they exist precisely so the UI can stay responsive (see below).

## Pages / screens (in `actors_and_surfaces`)

For each surface, capture: **name · purpose · responsibilities · entry/exit · what it MUST let the user do or see.** Specify responsibilities and guarantees, not pixel layout or component arrangement (that's design/code).

> Surface: **Expense Review**. Purpose: confirm/correct an extracted expense before saving. Entry: from capture flow once extraction starts. Exit: on save (→ list) or discard. MUST allow editing every extracted field; MUST indicate low-confidence fields; MUST NOT require the user to re-enter data the extractor already produced.

## Widgets / components (in `requirements`)

Specify a widget **only** when it carries a normative behavior contract clients depend on — and then specify the *contract*, never the prop list. Bind it to a `REQ-` when there's a guarantee:

> REQ-XXX: The amount field MUST reject non-monetary input and MUST surface the rejection inline at the field without discarding other entered values.

If a widget has no guarantee beyond "it's a text box," it needs no requirement.

## Interactions (in `requirements`)

Specify interactions as **event → effect contracts** — what MUST happen, observably, when the user acts:

> REQ-XXX: Submitting the form with an invalid field MUST surface `ERR-XXX` inline at the offending field, MUST keep the user on the surface (MUST NOT navigate away), and MUST preserve all entered values.

Keyboard shortcuts are normative **only** when they're a guaranteed binding (e.g., "Esc MUST cancel an in-progress capture"). Convenience accelerators that merely mirror a visible control are code, not spec.

## Error & warning surfacing (in `failure_modes` + `requirements`)

Every user-facing failure MUST have a `failure_mode` whose `behavior` describes the **observable UI surface**, not just an HTTP code:

```yaml
failure_modes:
  - code: ERR-EXP-001
    condition: OCR extraction returns low-confidence fields
    behavior: Surface affected fields as warnings inline; allow save; do not block.
  - code: ERR-EXP-002
    condition: Save request fails (network/permission)
    behavior: Enter Error state; show actionable message; preserve edits; offer retry.
```

The normative rule that errors are never swallowed (console-only / silent) belongs as a `REQ-` or a cross-cutting invariant, not buried in one failure mode.

## Progress reporting and non-blocking (in `requirements`)

Two related guarantees, both expressed as observable behavior (never as an implementation like "use a web worker" — that's `how`, golden-rule D):

> REQ-XXX (progress): Any operation exceeding a perceptible delay MUST report progress — determinate when the total is known, indeterminate otherwise — naming what is in flight; cancelable where applicable.
>
> REQ-XXX (responsiveness): The surface MUST remain interactive while work is in flight — scrolling, typing, and navigation MUST NOT be blocked by extraction, save, or rendering of large results.

State the *contract* (UI stays responsive; progress is visible), not the mechanism (workers, async, virtualization) — a clean-room implementation may choose differently.

## Tiny worked example

```yaml
state_and_lifecycle: |
  States: Empty, Extracting, Review, Saving, Error. Initial: Empty.
  Transitions (event [guard] → target / effect):
    addReceipt        → Extracting   / extraction begins, progress shown, UI stays interactive
    extracted         → Review       / fields prefilled; low-confidence flagged (ERR-EXP-001)
    extractFailed     → Error        / ERR-EXP-003 surfaced; allow manual entry
    save [valid]      → Saving        / persist begins, progress shown
    saved             → (list)
    saveFailed        → Error        / ERR-EXP-002 surfaced; edits preserved; retry offered
  During Extracting/Saving the surface MUST stay interactive and MUST ignore stale
  extraction responses for a receipt the user has replaced.

requirements:
  - id: REQ-EXP-001
    summary: Invalid amount handling
    level: MUST
    text: |
      Submitting with a non-monetary amount MUST surface ERR-EXP-004 inline at the
      amount field, keep the user on Review, and preserve all other fields.

failure_modes:
  - code: ERR-EXP-002
    condition: Save fails (network/permission)
    behavior: Enter Error; show actionable message; preserve edits; offer retry.
```
